# Улучшения памяти и нейросетевой части

Изменения основаны на чтении кода. Полного прогона с реальными моделями (sentence-transformers, faiss, LM Studio) не делалось: в среде их нет. Проверено так:
- `tests/test_improvements.py` — 20 юнит-тестов чистой логики (пластичность, онлайн-обучение, калибровка). Запуск: `python -m unittest tests.test_improvements`.
- `tests/smoke_memory_stubs.py` — реальные методы `CognitiveMemory` (с заглушками faiss/sentence_transformers): асимметрия STDP, метапластичность, масштабирование хабов, обучение весов по `apply_feedback` и их восстановление после перезапуска.
- `tests/identity_critic_check.py` — критик идентичности на методах из `routes/ai_assistant.py` (с фейковым эмбеддером и цепочкой ТЕКУЩЕЕ_Я).

## Что сделано

1. **STDP с реальным порядком событий** (`GCN/memory_graph.py`, `_hebbian_update`). dt = t_post − t_pre по времени событий обоих узлов, направления учитываются отдельно. Раньше dt считался от last_activation синапса, и окно почти никогда не срабатывало.
2. **Реальные времена реплик**. `Episode` хранит `user_ts`/`assistant_ts`; `user_ts` фиксируется в `_prepare_messages`, `assistant_ts` — при сохранении. Если времени нет (старые данные), используется прежнее смещение.
3. **Метапластичность** (`GCN/plasticity.py`). Пластичность = max(floor, initial / (1 + k·n)) по числу подтверждений. Раньше порог стабилизации был недостижим для шагов обычной ветки.
4. **Синаптическое масштабирование** (`_scale_synapses`). Входящая и исходящая сила узла ограничены `SYNAPSE_NODE_STRENGTH_CAP`, вызывается в `deep_consolidation`.
5. **Онлайн-обучение весов поиска по обратной связи** (`GCN/learned_rerank.py`). Признаки каждого результата запоминаются при поиске (`_record_retrieval_features`). `apply_feedback` обновляет веса логистической регрессией с L2 к априорным значениям. Веса сохраняются в `<cognitive_memory>/rerank.json` и загружаются при перезапуске. Ручная корректировка весов рефлексией LLM продолжает работать, но перезаписывается при следующем обучении.
6. **Консолидация по числу эпизодов** (`add_episode` → `_run_triggered_consolidation`). Помимо таймера, запускается после `DEEP_CONSOLIDATION_EPISODE_TRIGGER` новых эпизодов.
7. **Критик идентичности** (`routes/ai_assistant.py`). Сравнивает ответ с текущей версией ТЕКУЩЕЕ_Я (последний валидный голос цепочки), а не с топологическим ядром. Один эмбеддинг на текст вместо двух.
8. **Калибровка порогов** (`GCN/calibration.py`, `tools/calibrate_thresholds.py`). Пороги выбираются максимизацией F1 по размеченным парам. Результат пишется в `GCN/calibration.json` и подхватывается `config_ai.py`.
9. **Размерность эмбеддингов**. `EMBEDDING_DIM` приведён к 1024 (multilingual-e5-large). Раньше стояло 384 от MiniLM, а в `GCN.py` — fallback 128.
10. **Бюджет памяти в промпте** (`MEMORY_CONTEXT_MAX_CHARS`). Факты добавляются по убыванию релевантности до лимита символов.
11. **Единая рабочая память**. Показанные модели факты добавляются в `hierarchy`, которая задаёт стартовый узел графового поиска.

## Что не сделано (и почему)

- **Структурированный вывод LLM (JSON schema)** для извлечения фактов, противоречий и ревью. Нужно менять все точки вызова в `llm_client` и парсеры; это отдельная итерация.
- **Предиктор переходов на эмбеддингах (MLP/GRU)** вместо текстовых ключей. Нужны torch и обучающие данные из реальных диалогов.
- **Разделение времени события и времени записи**. Требует поля в схеме GCN-объектов и миграции данных.
- **NLI-модель для противоречий** вместо LLM на каждую пару. Нужна отдельная модель и калибровка.
- **Структурированная идентичность и хеш-цепочка**. Схема ТЕКУЩЕЕ_Я меняется, и это решение должны принимать вы.
- **Улучшения memory viewer** (толщина рёбер по весу, подсветка активации, дифф Hebbian-обновлений, очередь противоречий). Это работа в `static/memory_viewer.html` и `memory_viewer_core.py`; запланирована отдельно.
- **Значения порогов по умолчанию** (`IDENTITY_HANDSHAKE_THRESHOLD = 0.25`, `IDENTITY_CONSISTENCY_THRESHOLD = 0.35`) не менял: нужны реальные размеченные пары для калибровки.

## Как калибровать пороги

Файл pairs.jsonl, одна строка на пример:
`{"kind": "handshake", "a": "новая версия", "b": "предыдущая версия", "same": true}`
`{"kind": "consistency", "a": "ответ ассистента", "b": "текст ТЕКУЩЕЕ_Я", "same": false}`

Запуск: `python tools/calibrate_thresholds.py pairs.jsonl`. Для калибровки нужно хотя бы несколько десятков примеров каждого вида, иначе порог будет случайным.

## Новые переменные окружения

SYNAPSE_NODE_STRENGTH_CAP (3.0), PLASTICITY_FLOOR (0.05), PLASTICITY_STABILIZE_K (0.1), DEEP_CONSOLIDATION_EPISODE_TRIGGER (20), RERANK_LEARNING_RATE (0.01), RERANK_L2 (0.05), RETRIEVAL_FEATURE_CACHE_SIZE (500), MEMORY_CONTEXT_MAX_CHARS (3500).


# Раунд 4: схемы LLM, время события, NLI, предиктор переходов

Проверено: `tests/test_round4.py` (17 тестов, включая сверку градиента с конечными разностями и гейт на случайных данных), `tests/test_llm_response_format.py` (настоящий HTTP-сервер: отказ по схеме -> повтор без неё), `tests/contradiction_flow_check.py` (порядок NLI и LLM, отказ по схеме), `tests/transition_integration_check.py` (обучение и использование предиктора в `CognitiveMemory`).

1. **JSON schema для LLM.** `GCN/json_schema.py` содержит схемы вердикта противоречий и списка фактов, плюс минимальный валидатор. `llm_client.call_llm` / `call_llm_raw` передают `response_format`; при 400 повторяют запрос без схемы. Схема включена в верификатор противоречий и в экстрактор фактов из поиска. Не переведены: ревью viewer, рефлексия весов, вопросы для поиска (там свободный текст).
2. **Предиктор переходов на эмбеддингах.** `GCN/transition_model.py`: двухслойная сеть на numpy с ручным градиентом (torch не нужен). Обучается на парах соседних реплик в `deep_consolidation`. Принимается гейтом: на отложенной выборке hit@k должен превышать базовый уровень «популярность концептов» на margin. Иначе не используется. Файл `transition.npz` в каталоге пользователя. Используется в `predict_next`, если принят.
3. **Время события.** `GCN/temporal.py` нормализует даты из экстрактора. Дата сохраняется в `object["event_time"]` при записи, попадает в результаты поиска и показывается в контексте как «событие ...». Свежесть поиска по-прежнему считается по `last_accessed`/`created`: событие и запись разделены, но поиск по «когда» не добавлен.
4. **NLI для противоречий.** `GCN/nli.py`. Если задана `NLI_MODEL`, NLI решает до LLM: entailment или neutral с вероятностью >= `NLI_DECISION_THRESHOLD` -> ложное противоречие без вызова LLM. По умолчанию выключено (`NLI_MODEL` пуст). Порядок меток и порог не откалиброваны.

## Что не проверено

- Реальная NLI-модель (Hugging Face не в списке разрешённых доменов песочницы), порядок меток и порог.
- Реальная LM Studio с `response_format`: проверено на тестовом сервере.
- Полный путь `event_time` через `router.retrieve` и повторный поиск: проверены отдельные части.
- Предиктор на реальных диалогах: проверен на синтетической цепочке тем. Стоимость обучения: до 1000 пар эмбеддингов на каждую консолидацию.

## Новые переменные окружения

NLI_MODEL (пусто), NLI_LABELS (contradiction,entailment,neutral), NLI_DECISION_THRESHOLD (0.85), TRANSITION_TOP_K (5).

# Раунд 5: агентный цикл инструментов

Что было не так: предвыбор инструментов по подстрокам скрывал от модели часть инструментов; цикл останавливался после первого успешного раунда для «простых» запросов, поэтому цепочки («найди в памяти → исправь») обрывались; fast-router мог увести запрос в прямой ответ без инструментов; в памяти не было инструментов редактирования; картинку нельзя было рассмотреть повторно.

Что сделано:

1. **Модель решает сама** (`GCN/tool_router.py`). Ранжирование `rank_tools` упорядочивает инструменты и ограничивает их число (`TOOL_NATIVE_MAX`), но не скрывает их жёстко. Core-набор (recall, remember, web_search) доступен всегда.
2. **Настоящий цикл.** Продолжается, пока модель вызывает инструменты. Останавливается по причинам, которые видны в `stop_reason`: `model_done`, `round_limit`, `call_limit`, `no_progress`, `stuck`, `failures`, `user_skip`.
3. **Обнаружение зацикливания.** Повтор одного и того же вызова (с учётом регистра и пробелов) не выполняется, модель получает прежний результат. После `AGENT_STUCK_LIMIT` повторов цикл завершается с подсказкой отвечать по собранному.
4. **Пропуск шага.** `ToolRouter.request_skip()` прерывает ожидание инструмента и отдаёт управление ответу. Endpoint `POST /ai/chat/skip_tools`, кнопка «Пропустить» в строке статуса.
5. **Маршрутизация.** `might_need_tools()` не даёт запросу с маркерами инструментов уйти в прямой ответ.
6. **Память: цепочка правок** (`GCN/memory_tools.py`). `memory_search` (возвращает id), `memory_explain`, `memory_forget` и `memory_update`. Удаление и замена идут в два шага: предпросмотр, затем `confirm=true`. Без предпросмотра в течение 10 минут изменение не выполняется. Подстрока короче 4 символов не принимается.
7. **Изображения** (`GCN/vision_tools.py`). `inspect_image` вырезает область (доли 0..1) и задаёт модели точный вопрос только по ней. Можно вызывать несколько раз: обзор, затем зум.

Тесты: `tests/test_agent_loop.py` (8 сценариев), `tests/test_tool_router.py` (7 старых сценариев сохранены).

# Раунд 6: анализ агентности и исправления

Проверено несколько проходов по проекту: маршрутизация (fast-router, предвыбор, пропуск роутера после поиска), состояние между ходами, инструменты и их схемы, защита от зацикливания, наблюдаемость в UI.

Найдено и исправлено:

1. **Роутер пропускался после поиска.** `search_answer_needs_no_tools` отключал агента для любого хода с поиском, если в запросе не было маркеров «другой задачи». Регулярка не знала глаголов правки памяти. Теперь роутер не пропускается, если `might_need_tools()` видит маркер инструмента, а регулярка дополнена (исправ, измени, обнови, сравни, затем и др.).
2. **Результаты инструментов терялись между ходами.** Фраза «удали то, что я сказал выше» не работала без повторного поиска, потому что `fact_id` не сохранялся. Теперь `_record_tool_digest` сохраняет краткие записи о вызовах последних четырёх ходов, и они передаются роутеру через `context_notes`. В историю диалога они не попадают.
3. **Агент не мог спросить.** Добавлен инструмент `ask_user` (`GCN/agent_tools.py`). Успешный вызов завершает цикл (`stop_reason='ask_user'`), вопрос возвращается в `pending_question`.

Тесты: `tests/test_agent_loop.py`, 10 сценариев.

Не реализовано, рекомендовано:
- Явный план для многошаговых задач и сохранение его между ходами.
- Предварительный детерминированный поиск (`_force_search_if_requested`) по ключевым словам всё ещё запускается до решения модели. Его стоит перевести на инструмент `web_search`.
- Рефлексия (`_reflect_on_failure`) делает отдельный LLM-вызов на каждый сбой. Стоит ограничить бюджетом.
- Оффлайн-набор примеров для оценки решений роутера.
- `stop_reason` и `pending_question` пока не выводятся в UI.

Также возможны: таймаут `LLAMACPP_STARTUP_TIMEOUT` при медленной загрузке большой модели (тогда сервер гасится и поднимается при следующем запросе) и `UVICORN_MODE=dev` (reload перезапускает приложение и заново поднимает модель).

# Раунд 9: автономный режим модели

Состояние до изменения: `AUTONOMY_ENABLED` и `AUTO_RESEARCH_ENABLED` были захардкожены в `True`, отключить без правки кода было нельзя.

Что делает автономность (`GCN/autonomy.py`), когда пользователь не пишет 5 минут и генерация не идёт, раз в ~45 секунд:
- синхронизирует цели с памятью и чистит старые цели;
- раз в 10 минут генерирует «эндогенные» цели и записывает их в память;
- выполняет исследовательскую очередь: LLM-вызовы и веб-поиск;
- собирает дайджест уведомлений.

Суточный лимит фоновых LLM-вызовов (`RESOURCE_BUDGET_LLM_CALLS`, `_consume_autonomous_llm_budget`) ограничивает эту активность, но не обычные ответы в чате.

Изменение: оба флага читаются из окружения, по умолчанию `1` (прежнее поведение). Чтобы отключить: `AUTONOMY_ENABLED=0` и `AUTO_RESEARCH_ENABLED=0` в `.env`.

Рекомендация: для личного ассистента автономность сейчас избыточна. Она занимает GPU фоновыми вызовами и пишет в память цели, которых пользователь не ставил. Новый агентный цикл покрывает явные запросы, а исследования можно запускать по запросу через инструмент постановки темы.

# Раунд 10: полное выключение автономности

Проблема: `AUTONOMY_ENABLED=0` и `AUTO_RESEARCH_ENABLED=0` выключали только главный цикл движка. Фоновые LLM-циклы из контроллера (`_periodic_planning` — генерация целей и запись их в память, `_periodic_reflection` — рефлексия) запускались всегда и флагами не гасились. Стабилизатор памяти (`STABILIZER_AI_REVIEW`, по умолчанию включён) тоже делал LLM-вызовы после консолидации.

Исправлено:
- `routes/ai_assistant.py`: при `AUTONOMY_ENABLED=0` не запускаются `AutonomyEngine`, `_periodic_planning` и `_periodic_reflection`. `_periodic_research` запускается, только если включён хотя бы один из двух флагов.
- `GCN/memory_graph.py`: AI-ревью стабилизатора выполняется только при `AUTONOMY_ENABLED=1`.
- Консолидация памяти и idle-обслуживание без LLM для целей остаются всегда.

Проверено: пробный запуск `_start_background_tasks` с заглушками тяжёлых модулей. При обоих флагах `0` запускаются только `_consolidation_task` и `_idle_task`. По умолчанию запускаются все пять.

Не проверено целиком: что `AutonomyEngine` не стартует при выключении в живом сервере. Проверено по коду и через пробный запуск контроллера с заглушками.

# Раунд 11: идентичность — ворота, карантин и явный выбор модели

Проблемы, найденные в текущей реализации:
- `contribute_to_identity` и `merge_identity_branches` писали в **общее курируемое ядро** (слой по умолчанию `shared`), без проверки содержания и происхождения.
- Чтение (`_get_identity_block`) смешивало личную и общую цепочку, и модель не видела, откуда запись.
- Нигде не было границы «память или идентичность»: факты и самоописание принимались одним инструментом.

Что сделано:
- `GCN/identity_gate.py` — ворота: классификация identity/memory/noise, отказ на шум (код, JSON, служебные маркеры, id), на факты (даты, адреса, телефоны), на формулировки без дословной опоры в диалоге (`evidence`), на дубликаты головы.
- `GCN/identity_quarantine.py` — карантин кандидатов: JSON на пользователя, подтверждение в разные дни (`IDENTITY_MIN_DAYS`), TTL 30 дней, атомарная запись.
- `GCN/identity_tools.py` — инструменты `identity_propose` и `identity_commit`. Запись только в личный слой, после подтверждения, с повторной проверкой ворот.
- `GCN/internal_tools.py`: `contribute_to_identity` отключён (возвращает отказ с инструкцией), `merge_identity_branches` пишет только в личный слой. Регистрация новых инструментов.
- `routes/ai_assistant.py`: блок ТЕКУЩЕЕ_Я читает только личную цепочку; общее ядро показывается отдельно и помечено «только чтение»; текст обрезан до 600 символов.
- `GCN/config_ai.py`: `IDENTITY_MIN_DAYS`.
- `GCN/tool_router.py`: маркеры идентичности направляют к `identity_propose`/`identity_commit`.
- `docs/IDENTITY_DESIGN.md` — описание трёх слоёв, жизненного цикла звена и ограничений.

Тесты: `tests/test_identity_gate.py`, 8 проверок (шум, факты, опора, дубликаты, подтверждение по дням, TTL, запись только в личный слой). Остальные наборы проходят.

# Раунд 12: общее ядро личности и человеческий гейт

Что сделано:
- `GCN/global_identity.py` — общее ядро развивается из опыта разных пользователей (пул обобщений по хешу пользователя), но меняется только через предложения, которые решает администратор.
- Предложение содержит точную формулировку, цель апгрейда, закрываемый вопрос цепочки и основание (число пользователей, без персональных данных).
- Администратор (`MCP_ADMIN_USERS`) получает уведомление через существующий канал `/notifications/poll` и отвечает в чате «да» / «нет» / «откатить ядро». Ответ перехватывается до генерации; обычные сообщения не затрагиваются.
- Применение — новое звено в shared-слое; откат — invalidate с причиной. Журнал решений в `ai_memory_v3/global_identity.json`.
- `GCN/identity_tools.py`: подтверждённая личная идентичность учитывается в пуле.
- `routes/ai_assistant.py`: блок идентичности показывает два слоя — общее ядро (только чтение, с пометкой) и личную цепочку пользователя; `chat_with_ai` перехватывает ответы администратора; `poll_notifications` отдаёт администратору предложения.
- Защиты: порог пользователей (`GLOBAL_IDENTITY_MIN_USERS`, 3), запрет инструкций, интервал 7 дней между применениями, истечение предложений через 14 дней, отсутствие повторов.

Тесты: `tests/test_global_identity.py`, 7 проверок. Остальные наборы проходят.

Не проверено на живом сервере: маршрут `chat_with_ai` с перехватом гейта и доставка уведомления в UI. Логика гейта проверена функциями; HTTP-слой — по коду.

# Раунд 13: v9 — упрощённая схема личности и общего ядра

Версия v8 не рекомендуется к выпуску: гейт перехватывал «да»/«нет» администратора даже без ожидающего предложения (такой ответ не попадал в модель), а системно сгенерированный вопрос цепочки уходил в общее ядро. Пул обобщений собирал личные формулировки разных пользователей.

Что сделано в v9:
- Удалены `GCN/global_identity.py`, пул обобщений, автоматические предложения и уведомления администратора.
- Добавлен `GCN/core_admin.py`: общее ядро меняет только администратор командами «ядро: …», «да»/«нет», «откатить ядро». Подтверждение принимается только при ожидающем предложении и в течение 10 минут.
- `routes/ai_assistant.py`: гейт администратора — `core_admin.handle_admin_message`; блок идентичности показывает общее ядро (только чтение) и личную цепочку.
- `GCN/identity_tools.py`: подтверждённая личная идентичность больше не учитывается в пуле.
- Личные инструменты (v7): `identity_propose`, `identity_commit`, гейт и карантин без изменений.

Тесты: `tests/test_core_admin.py`, 8 проверок, включая регрессию «да» без предложения. Остальные наборы проходят.

Не проверено на живом сервере: HTTP-путь гейта в `chat_with_ai` и отображение блоков в контексте.

# Раунд 14: команды администратора в естественной форме

- «запиши в ядро» / «обнови ядро» без текста: модель составляет формулировку из последних реплик диалога (`_draft`), администратор видит её и подтверждает «да». Модель ничего не записывает сама.
- «ядро: <текст>» остаётся как явная форма с точным текстом.
- Черновик модели проходит ту же проверку, что и текст администратора. Без доступной модели система просит текст в явной форме.
- Тесты: `tests/test_core_admin.py`, 11 проверок.
